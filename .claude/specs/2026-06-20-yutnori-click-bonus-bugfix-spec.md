## 1. 버그 B — 빈 바닥 클릭이 HOME 말을 출발시킴

### 1-1. 사용자 신고 원문

> "결과 누른 후 말을 눌러야 하는데 빈 바닥을 눌렀더니 시작 말이 나갔다. 내 돌을 눌렀을 때만 동작하게."

### 1-2. 재현 조건

- 내 차례 + 결과 칩(도/개/걸/윷/모) 선택 완료 상태.
- 보드 위의 **아무 말도 없는 빈 칸**(HOME 박스 영역도 아닌 보드 중앙부)을 클릭.
- 기대: 아무 이동도 일어나지 않고 안내만 표시.
- 실제: 첫 HOME 말이 자동으로 출발(이동)했다.

### 1-3. 근본 원인

`main.js` 보드 클릭 핸들러는 클릭 좌표를 3단계로 해석했다.

1. `pickMyPieceAt` — 보드 칸 위의 내 말 클릭 판정.
2. `isClickOnHomeArea` + `pickFirstHomePiece` — HOME 박스 영역 클릭 시 첫 HOME 말 선택.
3. **(문제의 폴백)** 위 둘에 모두 실패해도 `pickFirstHomePiece`로 **첫 HOME 말을 자동 선택**해 `movePiece`를 호출.

3단계 폴백 때문에 의도와 무관한 순수 빈 칸 클릭이 시작 말을 강제로 출발시켰다. 사용자는 "결과 선택 후 빈 곳을 잘못 눌렀을 뿐"인데 말이 나가는 오작동으로 인식했다.

### 1-4. 수정 방침

- 3단계 폴백(빈 칸 → 첫 HOME 말 자동 선택)을 **완전히 제거**한다.
- 1단계(내 말 직접 클릭) 또는 2단계(HOME 박스 영역 직접 클릭)에서 말이 특정됐을 때**만** 이동한다.
- 둘 다 실패하면 `이동할 말을 클릭하세요.` 안내(toast, error)를 띄우고 `return`(이동 없음).

### 1-5. 수용 기준 (AC)

- **AC-B1**: 결과 칩 선택 상태에서 보드 빈 칸 클릭 → 이동 0, `이동할 말을 클릭하세요.` 토스트 표시.
- **AC-B2**: 보드 위 내 말 클릭 → 정상 이동(기존 1단계 동작 회귀 유지).
- **AC-B3**: HOME 박스 영역 클릭 → 첫 HOME 말 정상 출발(기존 2단계 동작 회귀 유지).

## 2. 버그 C — 윷·모 보너스가 던지기+이동 이중 부여되어 던지기 리필

### 2-1. 사용자 신고 원문

> "모가 나와 한번 더 던져 개가 나왔는데, 개부터 이동시켰더니 윷던지기가 한번 리필됐다."

### 2-2. 재현 조건

- 모 던짐 → "한 번 더 던지기" 권리로 한 번 더 던져 개가 나옴 → 큐 상태 `['mo', 'gae']`.
- 이 상태에서 **개부터 이동**하고 모를 나중에 비우면, 정상적으로 끝나야 할 턴에 던지기가 한 번 더 리필되었다(추가 던지기 1회 부당 획득).
- 이동 순서를 바꿔 모를 먼저 비우면 리필이 발생하지 않는 **비대칭** 버그.

### 2-3. 근본 원인

2026-06-17 **버그 D**(윷·모로 말 이동 시 보너스 던지기 소실) 수정이 도입한 `bonusFromConsumed`가 원인이다.

버그 D 수정은 MOVE_PIECE / CHOOSE_PATH에서 소비한 결과를 큐에서 `splice`로 제거하기 **전에** `bonusFromConsumed = (useResult === 'yut' || useResult === 'mo')`를 계산하고, 이를 `hasBonus`에 포함시켰다. 목적은 "윷·모를 소비해 큐가 비더라도 보너스 던지기 권리를 보존"하는 것이었다.

그러나 이 모델은 보너스를 **던지기 시점이 아니라 이동(소진) 시점**에 부여한다. 그 결과:

- 모/윷에 대한 "한 번 더 던지기" 권리가 **던지기에서 한 번**(실제 보너스 던지기로 이미 행사) + **이동에서 또 한 번**(`bonusFromConsumed`) **이중**으로 평가된다.
- 큐 `['mo', 'gae']`에서 **모를 마지막에 비우면**, 마지막 소진이 `useResult === 'mo'`라 `bonusFromConsumed = true` → 큐가 비어도 `hasBonus = true` → `passTurn` 미호출 → 던지기 리필.
- 반대로 모를 먼저 비우면 마지막 소진이 `gae`라 `bonusFromConsumed = false` → 정상 턴 종료.

즉 **소진 순서(모를 마지막에 비우는지 여부)에 따라 리필이 발현**되는 비대칭 버그였다.

### 2-4. 수정 방침 — Option A: 던지기 시점 적립/소비 모델

보너스 던지기 권리를 **이동 시점 계산값(`bonusFromConsumed`)에서 분리**하여, `game.pendingThrows`라는 **별도 적립/소비 카운트**로 관리한다.

- **적립**: THROW_YUT 시점에 던진 결과가 `yut`/`mo`면 `pendingThrows += 1`.
- **소비**: THROW_YUT가 이미 적립된 보너스 던지기 권리를 행사한 것이면(`pendingThrows > 0`) `pendingThrows -= 1`. 즉 보너스 던지기 한 번이 권리 한 번을 소비.
- **이동 시점 보너스 부여 전면 제거**: MOVE_PIECE / CHOOSE_PATH에서 `bonusFromConsumed` 계산과 그에 따른 `hasBonus` 가산을 삭제.
- **턴 종료 판정 통일**: 모든 `hasBonus` 판정을 `game.capturedBonus === true || game.pendingThrows > 0`로 통일. 큐에 남은 결과의 종류(`lastResult`)는 보너스 판정에서 배제(큐가 비어야만 `passTurn` 후보가 되고, 윷·모 보너스는 던지기 시점에 이미 적립됨).
- **초기화**: `passTurn()`, `resetGame()`, `softResetRoom()`에서 `pendingThrows = 0`. STATE 스냅샷에 `pendingThrows` 노출(테스트/봇 관찰용, 후방 호환 추가 필드, 클라이언트 기존 동작 무영향). `/test/inject`에 `pendingThrows` 주입 지원.

이 모델에서는 "윷·모를 던진 횟수"만큼만 추가 던지기가 보장되며, 결과 소진 순서와 완전히 무관하다(버그 C 해소).

### 2-5. 버그 D와의 양립

던지기 시점 적립 모델은 버그 D(보너스 던지기 소실)도 동시에 막는다.

- 모를 던지면 `pendingThrows = 1`이 **적립**된다(큐 `['mo']`).
- 보너스 던지기를 행사하기 **전에** 모를 먼저 이동해 큐가 비어도, `pendingThrows = 1`이 **보존**되므로 `hasBonus = true` → 턴 유지 + 추가 THROW 허용(보너스 소실 없음).
- 즉 버그 D의 "이동 시점 큐 상태에 던지기 권리가 의존하던" 취약점이 제거된다. 권리는 던진 횟수에만 의존한다.

버그 C와 버그 D를 **하나의 모델**(`pendingThrows`)로 동시에 만족시키는 것이 본 수정의 핵심이다.

### 2-6. 수용 기준 (AC)

- **AC-C1 (소진 순서 무관)**: 큐 `['mo', 'gae']` + `pendingThrows = 0` 상태에서 **개 먼저 이동**하든 **모 먼저 이동**하든, 두 결과를 모두 소진하면 동일하게 `pendingResults = []`, `pendingThrows = 0`, 턴 교대(`currentTurn = 'p2'`) — **던지기 리필 없음**.
- **AC-C2 (이중 적립 0)**: 실게임 흐름(THROW로 mo → 보너스 THROW로 non-bonus)에서 보너스 던지기 행사 직후 `pendingThrows = 0`(윷·모를 여러 번 던져도 미소비 권리 1회분만 남고 보너스 던지기가 소비).
- **AC-C3 (버그 D 양립)**: 큐 `['mo']` + `pendingThrows = 1` 상태에서 보너스 던지기 행사 전에 모를 먼저 이동 → 큐는 비지만 `pendingThrows = 1` 보존, 턴 유지(`currentTurn = 'p1'`), 후속 THROW 허용(데드락/소실 없음).
- **AC-C4 (회귀 무손상)**: 기존 §6/§13-11/§13-12 보너스·잡기·capturedBonus 회귀(YR-C8 시리즈, qa-defect2 등) 전부 유지.
